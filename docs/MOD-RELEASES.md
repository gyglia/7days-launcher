# Как выпускать обновления сборки модов

Для лаунчера 1.4.0 и новее. Обновления модов публикуются в **[gyglia/jago-releases](https://github.com/gyglia/jago-releases/releases)**. Репозиторий `7days-launcher` предназначен для самого приложения.

## Коротко: где указать режим и дату

В файле **manifest.json**, который прикладывается к релизу модов. Дата публикации GitHub и текст описания релиза на расписание не влияют.

| Что нужно | Режим | Когда игроки обновятся |
| --- | --- | --- |
| Плановое обновление | `scheduled` | В указанную дату с 04:00 по Москве |
| Срочное обновление | `immediate` | После обнаружения опубликованного релиза |

В интерфейсе GitHub отдельного переключателя этих режимов нет. Режим задаётся в манифесте перед загрузкой файлов.

## 1. Подготовить новую сборку

1. Возьмите манифест предыдущей сборки и сохраните рабочую копию под именем `new-manifest.json`.
2. Измените `Version`, например с `sever2026.1` на `sever2026.2`. Тег нового релиза тоже назовите `sever2026.2`.
3. Для изменившихся модов подготовьте новые ZIP. Внутри ZIP должны быть папки модов с `ModInfo.xml`, без лишней внешней папки.
4. В описании каждого изменившегося пакета обновите `Sha256`, `Bytes`, `Folders` и `Url`. Пример адреса: `https://github.com/gyglia/jago-releases/releases/download/sever2026.2/ИмяПакета.zip`.
5. Неизменившиеся пакеты оставьте с прежними контрольными суммами и ссылками на старые релизы. В `Packages` должен оставаться **полный список нужных пакетов**, а не только изменения. Удаление пакета из списка означает удаление этого пакета у игроков.

Размер и SHA-256 ZIP можно получить в PowerShell:

```powershell
(Get-Item '.\ИмяПакета.zip').Length
(Get-FileHash '.\ИмяПакета.zip' -Algorithm SHA256).Hash
```

Скрипт расписания ниже меняет только режим и дату. Он не собирает моды, не вычисляет их контрольные суммы и не загружает файлы на GitHub.

## 2А. Плановый релиз — в 04:00 по Москве

Откройте PowerShell в корне репозитория лаунчера. В текущем рабочем проекте это папка `launcher-repository`. Положите туда `new-manifest.json` и выполните:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\installer\Set-ReleaseSchedule.ps1 -ManifestPath .\new-manifest.json -Mode scheduled -Date 2026-11-13 -PreviousTag sever2026.1 -OutputPath .\manifest.json
```

Замените:

- `2026-11-13` — на нужную **будущую дату** в формате год-месяц-день. Время скрипт сам поставит на 04:00 по Москве.
- `sever2026.1` — на тег предыдущей сборки, на которой игроки должны оставаться до срока.

Пример означает **13 ноября 2026 года в 04:00 по Москве**. Дата приведена для образца, сама инструкция ничего не назначает. Если указать прошедшую дату, сборка уже считается активной.

В выходном `manifest.json` появятся поля:

```json
"Schema": 2,
"ActivationMode": "scheduled",
"ActivateAt": "2026-11-13T04:00:00+03:00",
"PreviousManifestUrl": "https://github.com/gyglia/jago-releases/releases/download/sever2026.1/manifest.json"
```

Это фрагмент полного манифеста, а не отдельный файл. До срока лаунчер использует предыдущий манифест, в том числе при первой установке у нового игрока. После срока выбирает новую сборку. Старые манифесты и пакеты должны оставаться доступными.

Если заранее выпускаете несколько плановых релизов, каждый должен ссылаться на непосредственно предыдущий релиз, а даты должны идти по возрастанию. Лаунчер пройдёт цепочку и выберет уже действующую сборку.

## 2Б. Срочный релиз — сразу

Сначала обновите сервер и убедитесь, что он работает с нужной сборкой. Затем подготовьте манифест:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\installer\Set-ReleaseSchedule.ps1 -ManifestPath .\new-manifest.json -Mode immediate -OutputPath .\manifest.json
```

Дату и предыдущий тег здесь указывать не нужно. Скрипт установит `ActivationMode: "immediate"` и удалит поля плановой активации. Игроки начнут обновляться после обнаружения этого релиза.

## 3. Опубликовать на GitHub

1. Откройте Releases в `gyglia/jago-releases` и создайте новый релиз с тегом новой сборки, например `sever2026.2`.
2. Сначала сохраните его **черновиком**.
3. Прикрепите подготовленный файл строго с именем **manifest.json** и новые/изменившиеся ZIP, на которые он ссылается. Неизменившиеся пакеты могут оставаться в прежних релизах.
4. Проверьте версию, режим, дату и ссылки. Для планового релиза проверьте, что предыдущий манифест доступен по ссылке на его тег.
5. Опубликуйте как обычный релиз, **Latest**, без отметки **Pre-release**.

Для планового релиза публикация может быть заранее: установка начнётся не раньше `ActivateAt`. Для срочного — после обнаружения релиза. Отдельного переключения в 04:00 на GitHub не требуется.

## 4. Полный ZIP для ручной установки

Если прикладываете полный архив сборки, поместите в его корень:

```text
manifest.json
ИмяПакета1.zip
ИмяПакета2.zip
...все пакеты из манифеста
```

В архиве должен быть **тот же manifest.json с режимом и датой**, что и в релизе. Нужны все пакеты, включая неизменившиеся. Не добавляйте внешнюю папку или другие файлы. Не используйте `launcher-build-inputs.zip`: это другой формат для сборки приложения.

Игрок выбирает этот ZIP через настройки → «Выбрать архив» → «Готово». Плановый архив не установится раньше срока. Полный архив не скачивается автоматически: обычное обновление загружает только изменившиеся пакеты.

## Что происходит у игроков

- Проверка выполняется при открытии лаунчера и перед запуском игры.
- Если известный плановый срок наступил при открытом лаунчере, он проверит обновление в течение 15 секунд, когда не занят и игра закрыта.
- Работающая игра не прерывается. Обновление потребуется перед следующим запуском.
- Часовой пояс Windows не влияет: время сравнивается с указанным `+03:00`. Системные часы должны быть правильными.
- Без сети используется сохранённое расписание. Неизвестный новый релиз без сети обнаружить нельзя.
- Обновления самого лаунчера независимы от расписания модов.

## Если рестарт сервера переносится

Расписание **не проверяет успешность запуска сервера**. В назначенное время лаунчер считает новую сборку активной, даже если сервер ещё не обновлён.

Переносите дату заранее: заново подготовьте манифест с новой датой и замените файл в релизе; обновите также полный ZIP, если он опубликован. Учтите, что игроки могли сохранить старое расписание или скачать старый ZIP: правка на GitHub не отзывает такие копии мгновенно. Попросите игроков выполнить «Проверить» с доступом к сети и скачать исправленный архив. Простое изменение текста описания релиза дату не меняет.

Если часть игроков уже обновилась, согласуйте сборку сервера и клиентов отдельно; не рассчитывайте на перенос даты как на гарантированный откат.

## Как поручить выпуск обновления в чате

Плановое: «Выпусти сборку sever2026.2. Плановое обновление 13 ноября 2026 в 04:00 по Москве. Предыдущая сборка sever2026.1».

Срочное: «Выпусти сборку sever2026.2 как срочную. Сервер уже обновлён».
